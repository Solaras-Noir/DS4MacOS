## Questions for the architect

None that block. Notes for M1 planning:
1. Feature report `0x05` is read at 64 bytes as specified. The Linux driver reads the calibration report at
   41 bytes. If the Bluetooth `dump` logs a failed read, that is the likely cause.
2. The real `xinput1_4.dll` exports `XInputGetAudioDeviceIds`, and the stub does not (the spec's export list
   follows xinput1_3). If the game refuses to load the stub as `xinput1_4`, add it in M3b.
3. Rumble sets both valid_flag0 bit 0 and valid_flag2 bit 2 (compatible vibration and vibration 2),
   so it works on old and new firmware alike. The lead decided this; the Mac outputs test confirms it.

## Deviations from the spec

1. Branch: the spec names `m0/scaffold`, but the cloud session harness assigned
   `claude/beautiful-goldberg-lw2lbh` and forbids pushing elsewhere without the owner's explicit
   permission. The session works on the assigned branch; the PR targets `main` as specified.
2. PR and CI operations went through the session's GitHub tools instead of `gh pr create` and `gh pr ready`.
3. T2 was reviewed by the lead directly instead of by a reviewer subagent. It was a placeholder scaffold of
   six small files, and the green CI on both jobs was the real check.
4. Extra `DualSenseCore` types beyond the spec: `StickState`, `DualSenseButtons`, `Dpad`, `BatteryStatus`,
   `BatteryState`, `MicLED`, and raw `l2Raw`/`r2Raw`. The probe also sends drag events while a mouse button
   is held, so aiming while firing moves the view. It also carries a fractional mouse-delta remainder,
   so small stick deflections still move the view.
5. Nits left for M1: doc comments on enum cases; no direct test of `TouchPoint(isTouching:id:x:y:)`.
6. CI warning, not ours: `actions/checkout@v4` runs on Node 20, which is deprecated. The workflow was not
   changed (T2 step 4 allows changes only for failures).
